# אפיון מערכת תחבורה ציבורית בשטחים סגורים

**CampusBus** — מערכת רב־אזורית לניהול נסיעות אוטובוס, נהגים, תחנות, קווים, ETA ותפעול בזמן אמת.

> אפיון מוצר ומערכת ברמת High-Level / Functional. אינו מסמך Low-Level Design.
> התרחיש, השמות והנתונים במסמך ובאב־הטיפוס בדויים לחלוטין.

---

## 1. תקציר מנהלים

מטרת המוצר היא לספק מערכת תחבורה ציבורית פנים־אזורית, המיועדת בראש ובראשונה להפעלת אוטובוסים בתוך שטחים סגורים כגון קמפוסים, פארקי תעשייה ומתחמים גדולים. המערכת אינה מתכננת תחבורה אל מחוץ לאזור השירות, אלא מנהלת את כל מחזור החיים של התחבורה בתוך האזור: הגדרת המרחב, תחנות וקווים, לוחות זמנים, נסיעות פעילות, מעקב GPS, זמני הגעה, תפעול בזמן אמת, פידבק וניתוח ביצועים.

המערכת מתוכננת מראש לתמיכה במספר אזורי שירות נפרדים. כל אזור שירות מוגדר כ־Region באמצעות פוליגון גיאוגרפי, ובגרסה הנוכחית אסור ל־Regions לחפוף זה לזה. כל המידע התפעולי והקונפיגורציה משויכים ל־Region, כך שניתן להוסיף אזורים חדשים בעתיד ללא שינוי קוד.

המוצר כולל שלושה ממשקים עיקריים: אפליקציית נוסע במובייל, אפליקציית נהג במובייל, ומערכת ניהול Web למחשב. בנוסף, נדרש כלי סימולציה פנימי לצורך בדיקת תרחישי נסיעה ו־GPS ללא נסיעה פיזית.

### 1.1 מטרות על

- להציג לנוסע מידע ברור ועדכני על קווים, תחנות, מיקום נהגים פעילים וזמני הגעה משוערים.
- לאפשר לנהג להפעיל נסיעה ולשדר GPS באופן פשוט, חסכוני בסוללה ועמיד להפרעות תקשורת.
- לאפשר למפעיל לנהל מרחוק את כל הקונפיגורציה והתפעול ללא deployment של האפליקציות.
- לתמוך במספר Regions באופן דינמי תוך שמירה על הפרדה ברורה של מידע והרשאות.
- לספק תשתית ל־ETA מתקדם, זיהוי סטייה ממסלול, Analytics, פידבק ושיפור מתמשך.
- לשמור ארכיטקטורה שמאפשרת בעתיד הרחבה לשירותי Mobility נוספים כגון טרמפים ותחנות On-Demand.

### 1.2 החלטות שכבר התקבלו

- אין ניהול Vehicles. מבחינת המערכת, נהג עם נסיעה פעילה הוא האוטובוס והמיקום שלו הוא מיקום האוטובוס.
- Regions אינם חופפים בגרסה הנוכחית. תמיכה בחפיפות תיבחן רק אם יופיע צורך עסקי עתידי.
- כל התחנות, הקווים, המסלולים, התמונות, לוחות הזמנים והגדרות התפעול מנוהלים מרחוק דרך מערכת הניהול.
- Carpool/טרמפים ו־On-Demand Stops באמצעות QR/Barcode הם Future Scope ויאופיינו בפירוט בשלב מאוחר יותר.
- פידבק ממשתמשים יהיה זמין ונגיש, אך לא פולשני ולא יכריח משתמש לדרג כל נסיעה.

## 2. גבולות המערכת ועקרונות מוצר

### 2.1 בתוך גבולות המערכת

- ניהול Regions גיאוגרפיים סגורים.
- ניהול תחנות, תמונות תחנה, קווים, מסלולים, כיווני נסיעה ולוחות זמנים.
- ניהול נהגים ומשתמשי מערכת הניהול.
- יצירה וניהול של Trips מתוכננים ופעילים.
- מעקב GPS אחרי נהגים במהלך נסיעה פעילה.
- הצגת מיקום בזמן אמת וחישוב ETA לנוסעים.
- זיהוי חריגה ממסלול מתוכנן.
- חיווי עומס באוטובוס באופן ידני על ידי הנהג.
- משובים, דירוגים, דיווחי תקלה, בקשות ומענה למשתמש.
- Analytics תפעולי ואיכות שירות.
- ניהול הודעות שירות, שינויים זמניים, Audit ו־Monitoring.
- כלי סימולציה לצורך בדיקות.

### 2.2 מחוץ לגבולות המערכת בשלב זה

- ניהול צי רכבים, מספרי רכב, טיפולים, דלק או תחזוקת Vehicle.
- נסיעות מחוץ ל־Region או תכנון מסלולים בין Regions.
- תשלומים, כרטוס או גבייה.
- Carpool/טרמפים בפועל — נשמר כיכולת עתידית בלבד.
- On-Demand Stop בפועל — נשמר כיכולת עתידית בלבד.
- זיהוי עומס אוטומטי באמצעות חיישנים/ראייה ממוחשבת — עתידי.

### 2.3 עקרונות תכנון

- Remote-first configuration: שינוי תפעולי נפוץ לא ידרוש שינוי קוד או פרסום גרסת אפליקציה.
- Region as root: רוב הישויות התפעוליות שייכות ל־Region אחד ברור.
- Safe configuration: שינויים משמעותיים יעברו Draft, Validation ו־Publish כדי למנוע טעויות מיידיות בפרודקשן.
- Graceful degradation: אובדן GPS או אינטרנט לא יגרום למערכת להציג מידע ישן כאילו הוא עדכני.
- No forced feedback: משוב תמיד זמין אך אינו מוצג באופן מציק או חוסם.
- Extensible mobility: המודל לא יהיה קשיח לאוטובוסים בלבד באופן שיחסום שירותים עתידיים.

## 3. משתמשים ותפקידים

| תפקיד | אחריות עיקרית |
|---|---|
| Passenger / נוסע | צופה בתחנות, קווים, ETA, עומס, מיקום נהגים פעילים, מועדפים ומגיש משוב או דיווח. |
| Driver / נהג | מפעיל נסיעה, משדר GPS, מעדכן עומס ידנית וצופה במידע הרלוונטי לנסיעה שלו. |
| Region Manager | מנהל קונפיגורציה ותפעול של Region אחד או יותר לפי הרשאה. |
| Dispatcher / מפעיל | צופה בתפעול החי, מטפל בחריגות, ביטולים ושינויים זמניים. |
| Support | מטפל בפניות משתמשים בלי לקבל בהכרח הרשאות שינוי תפעוליות. |
| System Admin | מנהל Regions, הרשאות מערכת והגדרות מערכתיות רחבות. |

ב־MVP ניתן להתחיל ממספר Roles מצומצם יותר מבחינת UI, אך מודל ההרשאות צריך להיות מסוגל להפריד לפחות בין נוסע, נהג, מנהל אזור ומנהל מערכת.

## 4. מודל הדומיין

| ישות | משמעות |
|---|---|
| Region | אזור שירות גיאוגרפי. כולל פוליגון, שם, סטטוס והגדרות. אינו יכול לחפוף Region אחר. |
| Stop | תחנה בתוך Region: שם, מיקום, תמונות, תיאור, סטטוס, QR ומטא־דאטה. |
| Line | קו תחבורה לוגי בתוך Region. |
| Route | מסלול גיאוגרפי וכיוון נסיעה של Line, כולל סדר תחנות. |
| Schedule | לוחות זמנים, שעות פעילות, ימים, תדירות וחריגים. |
| Trip | מופע תפעולי של נסיעה: Region + Line/Route + זמן + Driver + סטטוס. |
| Driver | נהג במערכת. בזמן Trip פעיל הוא מייצג את האוטובוס. אין Vehicle נפרד. |
| Passenger | משתמש נוסע; כולל העדפות/מועדפים לפי הצורך. |
| Location Sample | נקודת GPS של Driver במהלך Trip, עם timestamp ודיוק אם זמין. |
| Feedback / Service Request | משוב, דירוג, בקשה או תקלה; ניתן לקשר ל־Trip, Stop, Line או Region. |
| Announcement | הודעת שירות שמנהל מפרסם ל־Region. |
| Configuration Version | גרסת קונפיגורציה לצורך Draft, Validation ו־Publish. |
| Audit Event | רישום פעולה משמעותית שבוצעה במערכת הניהול. |

> **כלל דומיין — Driver אינו משויך ל־Vehicle. Trip פעיל משויך ל־Driver, ו־Driver הוא הישות שמספקת את המיקום שמוצג כאוטובוס לנוסעים ולמפעילים.**

## 5. Regions ו־Geofencing

### 5.1 הגדרה וניהול

- מנהל יכול ליצור Region על גבי מפה באמצעות ציור פוליגון.
- לכל Region: שם, מזהה, סטטוס Active/Inactive, פוליגון והגדרות תפעוליות.
- המערכת מבצעת Validation גיאוגרפי לפני שמירה/Publish.
- פוליגון חדש או ערוך לא יכול להצטלב עם Region קיים.
- תחנות ומסלולים של Region צריכים להימצא בגבולותיו, בכפוף ל־tolerance קטן שייקבע בהגדרות.
- אפשר להחזיק כמה Regions במערכת, כל עוד הם נפרדים גיאוגרפית.

### 5.2 התנהגות ביציאה מה־Region

מכיוון ש־GPS אינו מדויק לחלוטין, יציאה נקודתית מעבר לגבול לא תפסיק מיד את השירות. המערכת תשתמש ב־grace period ו/או buffer גיאוגרפי. הערכים עצמם יהיו קונפיגורביליים מרחוק.

- נהג ב־Trip פעיל: אם היציאה מה־Region נמשכת מעבר לסף שהוגדר, שידור ה־GPS הפעיל ייעצר או ה־Trip יסומן כחריג בהתאם לחוקי התפעול.
- נוסע: ההתנהגות המדויקת מחוץ ל־Region עדיין דורשת החלטה. ברירת מחדל מומלצת היא להפסיק שירות מבוסס־מיקום אך לאפשר צפייה במידע סטטי של Region שנבחר.

## 6. אפליקציית נוסע

האפליקציה מיועדת לשימוש מהיר ופשוט. הפעולות העיקריות צריכות להיות זמינות במספר קטן של צעדים, כאשר מרכז החוויה הוא “מתי האוטובוס מגיע ואיפה הוא עכשיו”.

### 6.1 מסכים מרכזיים

| מסך | תוכן מרכזי |
|---|---|
| Home / מפה | מיקום המשתמש אם ניתנה הרשאה, תחנות קרובות, נהגים פעילים/אוטובוסים, ETA ומצב שירות. |
| תחנה | שם, תמונה, קווים שעוברים בתחנה, הגעות קרובות, עומס רלוונטי, QR/קישור לתחנה. |
| קו / מסלול | מסלול על מפה, סדר תחנות, נהגים פעילים על הקו וזמני הגעה. |
| מועדפים | תחנות וקווים מועדפים לגישה מהירה. |
| משוב ופניות | דירוג נסיעה, דיווח תקלה, הצעה לשיפור, בקשה כללית וסטטוס טיפול. |
| פרופיל / הגדרות | הרשאות, שפה בעתיד, פרטיות והגדרות בסיסיות. |

### 6.2 ETA

ה־MVP כולל ETA בסיסי ומתקדם. אין חובה להשתמש ב־Machine Learning. ניתן להתחיל באלגוריתם דטרמיניסטי שמשלב מידע חי והיסטורי, ולשפר אותו עם נתונים שנאספים מהמערכת.

- מיקום GPS נוכחי ומהירות/כיוון.
- מיקום הנהג על גבי המסלול (map matching).
- זמני נסיעה היסטוריים בין מקטעי מסלול/תחנות.
- זמן ביום ויום בשבוע.
- זמני עצירה היסטוריים בתחנות.
- מצב חריג — סטייה מהמסלול, GPS ישן או תקשורת חסרה — צריך להשפיע על רמת האמון ב־ETA.

### 6.3 עומס

ב־MVP חיווי העומס מוזן ידנית על ידי הנהג ומוצג לנוסעים. רמות אפשריות לדוגמה: פנוי / בינוני / עמוס / מלא. הרשימה המדויקת תוגדר בהמשך. זיהוי עומס אוטומטי נשמר לפיתוח עתידי.

### 6.4 פידבק ופניות

- הגישה לפידבק תהיה זמינה מהתפריט וממסכי הקשר מתאימים, ללא popup שמכריח דירוג.
- חוות דעת על נסיעה: דירוג אופציונלי, קטגוריות וטקסט חופשי.
- דיווח תקלה: קטגוריה, תיאור, תחנה/קו/Trip לפי הקשר, ואפשרות תמונה לפי צורך.
- בקשה/הצעה לשיפור ופנייה כללית.
- המשתמש יכול לראות סטטוס טיפול ולקבל מענה מהמפעיל בתוך המערכת.
- המערכת שומרת metadata רלוונטי אוטומטית כדי לצמצם הקלדה — Region, קו, תחנה, Trip ושעה כאשר ההקשר ידוע.

### 6.5 QR בתחנה

לכל תחנה ניתן להפיק QR שמוביל ישירות לפרטי התחנה באפליקציה או ב־Web. התשתית הזו נמצאת ב־MVP. שימוש ב־QR לצורך “הפעלת” תחנה ודרישת עצירה הוא Future Scope נפרד.

## 7. אפליקציית נהג

### 7.1 זרימת עבודה עיקרית

- התחברות כנהג.
- צפייה בנסיעות הרלוונטיות לנהג/Region.
- בחירת/קבלת Trip והתחלת נסיעה.
- עם תחילת Trip מתחיל שידור GPS בהתאם להרשאות המכשיר ולהגדרות המערכת.
- במהלך הנסיעה הנהג יכול לעדכן עומס ידנית.
- המערכת מזהה סטייה מהמסלול ויכולה להציג לנהג חיווי, וכן להציג חריגה למפעיל.
- בסיום הנסיעה הנהג מסיים Trip והמעקב הפעיל נפסק.
- ביציאה ממושכת מה־Region מופעלת לוגיקת geofence/grace בהתאם להגדרות.

### 7.2 GPS ועמידות לתקשורת

- שידור GPS ברקע במובייל בזמן Trip פעיל.
- תדירות הדגימה והשידור ניתנת להגדרה מרחוק.
- במקרה של אובדן אינטרנט, האפליקציה שומרת נקודות זמנית ומנסה להשלים כאשר התקשורת חוזרת.
- השרת מחזיק timestamp של location אחרון ולא מציג מיקום ישן כאילו הוא Live.
- המערכת מטפלת ב־reconnects ומחדשת את חיבור ה־Realtime לפי הצורך.
- חיסכון בסוללה הוא דרישת מוצר; אין צורך במעקב מלא כאשר אין Trip פעיל.

### 7.3 Driver = Bus

> **החלטת Scope — אין בחירת רכב, אין סריקת רכב ואין ניהול צי. במסכים של הנוסע והמפעיל ניתן להציג “אוטובוס” כייצוג UI, אך הישות שמאחוריו היא Driver עם Trip פעיל.**

## 8. מערכת הניהול (Admin Web)

מערכת הניהול היא מקור האמת לקונפיגורציה ולתפעול. המטרה היא לאפשר פתיחת Region חדש ושינוי Region קיים ללא שינוי קוד, תוך Validation, Audit והרשאות מתאימות.

| מודול | יכולות עיקריות |
|---|---|
| Dashboard | תמונת מצב: נסיעות פעילות, חריגות GPS, סטיות מסלול, פניות פתוחות ומדדי שירות. |
| Live Operations | מפה עם הנהגים הפעילים, Trip, Line, location אחרון, freshness, ETA, עומס וחריגות. |
| Regions | יצירה/עריכה של פוליגונים, ולידציית אי־חפיפה, סטטוס והגדרות Region. |
| Stops | שם, נקודה, תמונות, תיאור, סטטוס, QR ושיוך לקווים. |
| Lines & Routes | ניהול קווים, כיוונים, פוליליין המסלול וסדר התחנות. |
| Schedules & Trips | לוחות זמנים, נסיעות מתוכננות, ביטולים ושינויים תפעוליים. |
| Drivers | ניהול נהגים, סטטוס ושיוך ל־Regions לפי צורך. ללא Vehicles. |
| Users & Roles | ניהול משתמשי Admin והרשאות; אפשרות גישה לפי Region. |
| Feedback | תיבת פניות, דירוגים, סינון, SLA פנימי, סטטוס ומענה למשתמש. |
| Announcements | הודעות שירות לפי Region ותקופת תוקף. |
| Analytics | מדדי נסיעות, ETA, איחורים, תחנות, עומס, פניות ואיכות שירות. |
| Configuration | פרמטרים דינמיים כגון GPS, grace, ספי off-route ו־ETA. |
| Audit Log | מי שינה מה ומתי. |
| Monitoring | בריאות השירות: stale GPS, clients, שגיאות תקשורת ומדדים טכניים בסיסיים. |
| Simulator | הפעלת Driver וירטואלי לאורך Route לצורך בדיקות. |

### 8.1 Draft → Validate → Publish

- שינויים בקונפיגורציה משמעותית נכתבים לטיוטה.
- לפני Publish רצות ולידציות: Region לא חופף, תחנות בתוך Region, מסלול תקין, סדר תחנות תקין, שדות חובה וכו'.
- Preview על מפה לפני פרסום.
- Publish הופך את הגרסה לזמינה לאפליקציות.
- ב־MVP נדרש לפחות Audit ויכולת לזהות מה פורסם. Rollback מלא לגרסה קודמת נשמר כיכולת עתידית.

### 8.2 שינויים תפעוליים זמניים

- השבתת תחנה לזמן מוגבל.
- ביטול Trip.
- הודעת שירות למשתמשים.
- שינוי זמני במסלול/לו״ז כאשר נדרש, תוך שמירה על ההגדרה המקורית.
- Active/Inactive או Archive במקום מחיקה פיזית עבור ישויות היסטוריות.

## 9. Trip Lifecycle ותפעול בזמן אמת

Trip הוא הישות התפעולית המרכזית. הוא מייצג נסיעה אחת בזמן מוגדר על Route מוגדר ומאפשר לחבר בין הקונפיגורציה לבין הפעילות החיה.

| סטטוס | משמעות |
|---|---|
| Scheduled | נסיעה מתוכננת שטרם התחילה. |
| Ready | אופציונלי: נסיעה זמינה לנהג/מוכנה להפעלה. |
| Active | הנהג התחיל את הנסיעה ומשדר GPS. |
| Completed | הנסיעה הסתיימה תקין. |
| Cancelled | הנסיעה בוטלה. |
| Exception | אופציונלי: מצב חריג תפעולי, למשל יציאה ממושכת מה־Region. |

- נהג יכול להיות ב־Trip פעיל אחד בלבד בכל רגע.
- Trip שייך ל־Region אחד בלבד.
- Location חי נשמר בהקשר של Trip כדי לאפשר ETA, Analytics וחקירת אירועים.
- לאחר סיום Trip אין צורך להמשיך מעקב GPS במסגרת האפליקציה.

## 10. ETA, Map Matching וזיהוי סטייה ממסלול

### 10.1 Map Matching

נקודת GPS אינה בהכרח נמצאת בדיוק על הכביש/Route. המערכת צריכה למפות את מיקום הנהג לנקודה סבירה על המסלול ולחשב התקדמות יחסית לאורכו. מידע זה משמש הן ל־ETA והן לזיהוי חריגה.

### 10.2 זיהוי Off-Route

- המערכת מחשבת מרחק מה־Route המתוכנן לאורך זמן.
- לא מייצרים חריגה בגלל נקודת GPS בודדת; משתמשים בסף מרחק + משך זמן/מספר דגימות.
- כאשר נוצרה חריגה, היא מוצגת ב־Live Operations ונרשמת כאירוע.
- ניתן להציג התראה לנהג בהתאם לעיצוב הסופי.
- ספי הזיהוי ניתנים לקונפיגורציה מרחוק.

### 10.3 ETA מתקדם ב־MVP

ה־ETA יתבסס על שילוב של נתוני Live ונתוני עבר. בשלב ראשון ניתן להשתמש בממוצעים/חציון לפי מקטעים ושעות, ללא מערכת ML מורכבת. המטרה היא להציג ETA שימושי ולא רק זמן תיאורטי לפי מהירות רגעית.

### 14.1 מבנה לוגי

- API מרכזי עבור קונפיגורציה, משתמשים, Trips, Feedback ו־Admin.

### 14.2 פריסה לענן (Deployment) והערכת עלויות

המערכת אינה תלויה בספק ענן מסוים. לצורך ה־MVP מומלץ להתחיל בארכיטקטורה פשוטה של Backend מנוהל, PostgreSQL מנוהל עם PostGIS, Hosting סטטי ל־Admin ו־Object Storage. אין צורך בשלב הראשון ב־Kubernetes, Microservices, Redis או Message Bus.

הערכות העלות להלן הן סדרי גודל לצורכי תכנון, נכון ל־15.09.2026. המחיר בפועל תלוי ב־Region, נפח תעבורה, שמירת Logs, Backups, High Availability, Data Transfer ומספר חיבורי Realtime. לצורך המרה בלבד נעשה שימוש בקירוב של דולר אחד ≈ 3.05 ש״ח.

| ספק ענן | מבנה מומלץ | Pilot / MVP | Production קטן |
|---|---|---|---|
| Microsoft Azure | App Service + Azure Database for PostgreSQL Flexible Server + Static Web Apps + Blob Storage | בין 30 ל־50 דולר לחודש (כ־90 עד 150 ש״ח) | בין 80 ל־200 דולר לחודש (כ־245 עד 610 ש״ח) |
| Amazon Web Services | App Runner + RDS for PostgreSQL/PostGIS + S3/CloudFront + Route 53 | בין 35 ל־70 דולר לחודש (כ־105 עד 215 ש״ח) | בין 80 ל־220 דולר לחודש (כ־245 עד 670 ש״ח) |
| Google Cloud | Cloud Run + Cloud SQL for PostgreSQL/PostGIS + Cloud Storage / Hosting סטטי | בין 20 ל־50 דולר לחודש (כ־60 עד 150 ש״ח) | בין 60 ל־180 דולר לחודש (כ־185 עד 550 ש״ח) |

Azure — ברירת המחדל המומלצת לפרויקט

- Backend: Azure App Service. תוכנית Linux Basic B1 מוצגת כיום בסדר גודל של כ־13.14 דולר לחודש, וניתן לעלות מדרגה כאשר העומס גדל.
- Database: Azure Database for PostgreSQL Flexible Server עם PostGIS. B1ms מוצג כיום בכ־12.41 דולר לחודש לפני Storage/Backups.
- Admin React יכול להתחיל ב־Static Web Apps, ותמונות תחנות/קבצים ב־Blob Storage. SSL ו־custom domain ניתנים לניהול כשירותי פלטפורמה.
- יתרון מרכזי: התאמה טבעית ל־.NET/ASP.NET Core ומעט יחסית עבודת תשתית. עבור המפתח בפרויקט זו ברירת מחדל פשוטה וסבירה.
AWS — חלופה גמישה ונפוצה

- Backend: App Runner הוא מסלול פשוט ל־container של ASP.NET Core; הוא מחויב לפי זיכרון provisioned וזמן CPU פעיל.
- Database: Amazon RDS for PostgreSQL. AWS תומכת רשמית ב־PostGIS, ולכן זו הבחירה המומלצת לפרויקט על פני DB זול יותר שלא הוכחה בו תמיכת PostGIS.
- Media/Admin: S3 + CloudFront לאתר/קבצים, Route 53 ל־DNS/domain.
- AWS יכולה להיות זולה מאוד ב־Pilot, אך יש בה יותר רכיבים ואפשרויות ולכן נדרש מעט יותר תכנון תשתית ו־IAM.
Google Cloud — חלופה יעילה לעומס התחלתי נמוך

- Backend: Cloud Run מתאים מאוד ל־ASP.NET Core container ומחויב לפי שימוש; ב־traffic נמוך ה־free tier עשוי להקטין משמעותית את עלות ה־Backend.
- Database: Cloud SQL for PostgreSQL תומך ב־PostGIS בכל גרסאות PostgreSQL העיקריות. Shared-core קטן מתחיל כיום סביב 0.0105 דולר לשעה לפני Storage/Backups, אך Production ידרוש בדרך כלל instance חזק יותר.
- Media/Admin: Cloud Storage ובמידת הצורך Hosting סטטי.
- יתרון מרכזי: עלות התחלתית נמוכה יחסית ב־workload לא רציף ו־autoscaling פשוט.

## 21. הגדרת Done ברמת מוצר ל־MVP

ה־MVP ייחשב מוצר שימושי מקצה לקצה כאשר ניתן לבצע את התרחיש הבא ללא שינוי קוד או התערבות ידנית ב־DB:

1. מנהל יוצר Region תקין שאינו חופף Region אחר.
2. המנהל מוסיף תחנות, תמונות, קו, Route ולו״ז ומפרסם את הקונפיגורציה.
3. המנהל יוצר/מנהל Driver והרשאות מתאימות.
4. Driver נכנס לאפליקציה, מתחיל Trip ומשדר GPS.
5. Passenger פותח את האפליקציה ורואה תחנות, קו, מיקום האוטובוס/Driver, ETA ועומס.
6. אם Driver סוטה מהמסלול או מפסיק לשלוח GPS, המערכת מזהה ומציגה את החריגה.
7. המפעיל רואה את ה־Trip ב־Live Operations ויכול לבצע פעולות תפעוליות בסיסיות.
8. Passenger יכול לשמור מועדף, לסרוק QR של תחנה ולהגיש משוב/תקלה.
9. Support/Admin יכול לענות לפנייה ולסגור אותה.
10. Analytics מציג נתונים מרכזיים כולל דיוק ETA, זמני נסיעה, סטיות ופידבק.
11. Simulator מסוגל להריץ את רוב התרחיש ללא Driver פיזי.

## 22. צעדי המשך מומלצים לאפיון

- לעבור מסך־מסך על Admin ולהגדיר שדות, פעולות והרשאות לכל מסך.
- לאפיין את אפליקציית הנהג כ־User Flow מלא, כולל edge cases של GPS, הרשאות ונעילת מסך.
- לאפיין את אפליקציית הנוסע ומבנה הניווט, כולל בחירת Region ומועדפים.
- להגדיר מודל Schedule/Trip סופי לפני תכנון DB.
- להגדיר API contracts ו־Realtime events.
- להגדיר סכימת DB ראשונית ויחסי הישויות.
- להגדיר acceptance criteria לכל MVP-XX ולהמיר ל־Epic/Story/Task.
- לאפיין את כלי הסימולציה מוקדם, משום שהוא יקצר משמעותית את מחזור הפיתוח והבדיקות.
> **הערת מסמך — זהו אפיון מוצר ומערכת ברמת High-Level/Functional Specification. הוא מספיק כדי ליישר קו על Scope וארכיטקטורה, אך לפני פיתוח מלא מומלץ להמשיך לאפיון מפורט של מסכים, API, DB ו־Acceptance Criteria.**
